# 第四轮：GEMM 分块搜索与主机开销（2026-10-21）

本轮实现了有契约检查的预绑定 GEMM，并完成有限配置搜索。固定配置预绑定的普通调用加速主要来自减少主机工作；分块收益由 CUDA Graph 同核对照单独验证。两类结果不能合并为通用 GPU 加速结论。

GPU 验证源码提交：`dc4bc8e3c87425bc1a90369b6df3b24f42689465`，工作树干净。Colab notebook（私人地址不随快照提供）。

## 实现与输入契约

- `prepare_matmul(a, b, bias, activation, config)` 一次验证输入并绑定张量对象、布局、分块和 launcher。每次调用仍检查存储指针、shape、stride、dtype、device 和梯度状态，返回新分配的输出。
- 允许原地更新输入内容；更换输入对象需要重新绑定。存储替换、布局或梯度状态变化会被拒绝。Graph 重放还要求遵守静态地址契约，不能认为 Python guard 会在每次重放时重新执行。
- `triton_prepared` 和 `triton_fused` 使用相同 `_gemm`、相同默认 tile 32/64/32、4 warps、2 stages、GROUP=8。预绑定没有更换计算公式，也没有复用输出缓冲来获得计时优势。
- `triton_prepared_search` 对预绑定实现搜索；原公开接口的 `triton_search`、`triton_pruned` 作为额外对照。工厂构建、首次调用、搜索和最终计时分别保存。
- CPU 仍通过项目 uv 环境工作；GPU 使用相同 `uv.lock`。Mac 不生成模拟 GPU 性能数据。

## 普通调用：主机开销占主导

event 协议保留 Python 提交间隙，另存 wall samples。下表为同 case、同轮配对加速比的三轮中位数；“快 1.82x”表示耗时约为对照的 1/1.82，而非耗时降低 82%。

| M/N/K | dtype | 固定预绑定 / 固定公开接口 | 搜索预绑定 / eager | 搜索预绑定 / 固定预绑定 |
|---|---|---:|---:|---:|
| 65/97/49 | FP16 | 1.823x | 2.122x | 1.011x |
| 65/97/49 | BF16 | 1.819x | 2.179x | 1.010x |
| 128/128/128 | FP16 | 1.817x | 2.031x | 1.013x |
| 128/128/128 | BF16 | 1.816x | 2.027x | 1.010x |
| 256/384/192 | FP16 | 1.841x | 2.033x | 1.001x |
| 256/384/192 | BF16 | 1.829x | 2.033x | 1.007x |
| 768/768/512 | FP16 | 1.841x | 1.950x | 1.001x |
| 768/768/512 | BF16 | 1.845x | 1.948x | 1.002x |

固定预绑定各案例中位数加速 1.816–1.845x，约降低 44.9%–45.8% event 耗时；全部单轮范围为 1.700–1.872x。这是预绑定输入契约下的 API 对比，不能归因于 GPU 算术吞吐提高。预绑定约 63 µs，而同核 Graph 重放只有约 2.8–16.8 µs，主机仍有显著优化空间。

普通调用的搜索相对固定预绑定仅约 0.1%–1.3% 中位数收益，部分单轮退化，配置选择也不稳定。普通公开接口的搜索同样经常选中不同配置。因此目前没有证据支持在每次短任务启动时在线搜索，或宣称已消除主机瓶颈。

## Graph：分块收益与同核控制

Graph 在侧流捕获多次调用、检查重放输出后计时，不代表普通 Python API 延迟。固定预绑定相对固定公开接口的各案例配对比值中位数为 0.998–1.001x；有一个 tail FP16 单轮低至 0.953x，原始值保留。总体符合相同设备内核的控制预期。

| M/N/K | dtype | 固定预绑定 µs | 搜索预绑定 µs | 搜索 / 固定预绑定（三轮配对中位数 [最小,最大]） | 搜索 / 兼容 compile |
|---|---|---:|---:|---:|---:|
| 65/97/49 | FP16 | 2.891 | 2.304 | 1.255 [1.253,1.256]x | 2.498x |
| 65/97/49 | BF16 | 2.890 | 2.301 | 1.256 [1.254,1.258]x | 2.501x |
| 128/128/128 | FP16 | 2.822 | 2.559 | 1.103 [1.076,1.106]x | 1.387x |
| 128/128/128 | BF16 | 2.841 | 2.571 | 1.104 [1.103,1.105]x | 1.513x |
| 256/384/192 | FP16 | 3.653 | 3.441 | 1.061 [1.060,1.062]x | 1.604x |
| 256/384/192 | BF16 | 3.660 | 3.431 | 1.067 [1.067,1.070]x | 1.820x |
| 768/768/512 | FP16 | 16.804 | 13.616 | 1.235 [1.234,1.237]x | 1.248x |
| 768/768/512 | BF16 | 16.395 | 13.241 | 1.239 [1.238,1.239]x | 1.263x |

各耗时列为各自三轮中位数，比值列为配对比值中位数，二者不必严格相除相等。额外分块收益为 1.061–1.256x，即约减少 5.7%–20.4% Graph 耗时。

Graph 下，search/pruned/prepared_search 在全部三轮中均对 tail/square 选择 `(32,32,32,4,2)`，对 medium/large 选择 `(64,64,64,4,3)`。这比普通调用搜索稳定，但仅覆盖有限候选，不能证明全局最优；BK、tile、stage 同时变化，也未隔离每个因素的贡献。pruned 在每轮三种搜索共 142 次尝试中仅节省 2 次，不支持“普遍大幅降低搜索成本”的结论。

## 主机分析与搜索成本

对 tail FP16 和 large FP16 分别完成三后端 cProfile 100 次调用及 CPU/CUDA Chrome trace。公开 Triton 接口每 100 次执行 `_validate_matmul` 100 次，累计约 7.64–7.69 ms，其中 `require_cuda` 累计约 4.38–4.47 ms；预绑定改为 guard 100 次和 tensor_signature 300 次，guard 累计约 1.22–1.28 ms。函数累计时间有包含关系，不可相加。

带 cProfile 的每调用观测约从公开接口 234 µs 降为预绑定 114 µs。该数值包含插桩开销和潜在驱动等待，只解释调用路径变化，不能替代前面的正式样本或当作纯 CPU 时间。每次预绑定仍运行 Triton JIT launch 分派并分配输出。

固定预绑定构建约 0.104–0.144 ms，首次调用另记。搜索成本包含候选构建、编译/缓存命中、正确性和采样：普通公开 search 约 0.298–2.130 s，Graph search 约 0.488–2.833 s。首次出现的配置及后续热缓存混合存在，不能将后运行的 prepared_search 成本更低完全归因于预绑定。

prepared_search 的 event 搜索约 0.168–0.175 s，Graph 约 0.444–1.027 s。以同轮 Graph 搜索成本除以相对固定预绑定节省的单次时间，粗略需要约 **27 万–377 万次**逻辑调用摊销。这个估算未控制冷缓存，也未计入全部应用接入与 Graph 构建成本；普通调用的小差值还会变号，不支持稳定回本承诺。后续应优先研究离线配置表及缓存复用。
